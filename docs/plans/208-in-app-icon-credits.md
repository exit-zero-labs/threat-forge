# Issue 208 — In-app icon credits and trademark notices

## Objective

A user running Threat Forge — browser or packaged desktop — can open one accessible surface
inside the application that lists every shipped icon project, license, and source, plus every
shipped third-party trademark owner and policy URL, with no network request. The list is
derived from `src/lib/registry/icon-entries.ts` and is proved equal to the `NOTICE` blocks by a
test that runs in `npm run ci:local`, so it cannot drift.

## Current behavior and evidence

Every claim below was read at `main` `73831f2` with a clean working tree.

### `NOTICE` is derived from the registry and already machine-audited

`NOTICE` is **not** generated by a script — there is no generator in `scripts/` (`ls scripts/`
shows eleven `.mjs`/`.sh`/`.ps1` files, none of which touch `NOTICE`). It is hand-maintained and
**held equal to the registry by a test**:

- `NOTICE:18-21` states the blocks are "derived from `src/lib/registry/icon-entries.ts` and
  verified for set equality by `src/lib/registry/provenance-audit.test.ts`".
- `provenance-audit.test.ts:126-150` is that audit. `attributionKey` (`:127-129`) builds
  `` `${project} — ${license} — ${sourceUrl}` `` per shipping entry and asserts the `Set` equals
  the `icon-attribution` block **in both directions** (`:131-135`). The trademark test
  (`:137-149`) does the same with `` `${label} — ${owner} — ${policyUrl}` `` against
  `icon-trademarks`.
- `parseNoticeBlock` (`provenance-audit.test.ts:34-46`) is the marker-delimited parser, and it
  `throw`s when a block marker is missing.
- `docs/runbooks/adding-an-icon.md:59-63` makes updating both blocks step 6 of adding an icon,
  and states that a mismatch "fails CI".

So the single source is **`ICON_ENTRIES`**, and `NOTICE` is already a downstream copy with a
build-failing equality gate. This is the fact that decides the design question in the issue.

### What the registry exposes today

`src/lib/registry/types.ts` carries everything the credits surface needs:

- `IconProvenance` (`:122-133`) — `project`, `sourceUrl` (documented "Absolute `https:` URL"),
  `sourceRef` (pinned version or SHA, never a moving ref), `license`, `copyright` (`""` for
  `CC0-1.0`/`Unlicense`).
- `IconTrademark` (`:141-148`) — a closed union of `{ kind: "none" }` and
  `{ kind: "third-party", owner, policyUrl, unmodified: true }`.
- `ShippedIconEntry` / `WithdrawnIconEntry` (`:160-173`) — the discriminant is
  `provenance: IconProvenance` vs `provenance: null`, mirrored by `artwork.kind`. A withdrawn
  entry carries `artwork.reason` and `artwork.fallbackIconId` (`:96-100`).

Measured contents of `ICON_ENTRIES` (`grep` over `icon-entries.ts`; the module header at
`:6-17` states the same numbers):

| Fact | Value |
|------|-------|
| Entries | 52 |
| `artwork.kind` | 44 `lucide`, 7 `paths`, 1 `withdrawn` |
| `trademark.kind` | 45 `none`, 7 `third-party` |
| Distinct provenance records | 4 — `LUCIDE`, `FEATHER_VIA_LUCIDE`, `SIMPLE_ICONS`, `SIMPLE_ICONS_KAFKA` (`:21-57`) |
| `NOTICE` attribution rows | 4 (`NOTICE:23-28`) |
| `NOTICE` trademark rows | 7 (`NOTICE:83-91`) |

**Withdrawn entries exist today: exactly one.** `aws` (`icon-entries.ts:460-473`) has
`artwork.kind: "withdrawn"`, `provenance: null`, `trademark: { kind: "none" }`, and
`status: "active"`. So the "ships no artwork" branch is **live behaviour, not an untestable
empty branch** — but it is a one-element list, and a future contributor restoring the
`amazonwebservices` mark would silently empty it. Step 1 covers the branch with synthetic
entries so coverage survives that; Step 2 additionally asserts the real row renders today.

Two details worth carrying into the UI copy, because they are easy to get wrong:

- `aws` has **no** trademark owner or policy URL (`trademark: { kind: "none" }`), so a withdrawn
  row cannot show one. `NOTICE:80-81` explains this in prose rather than in a machine block.
- No component defaults to `aws` (`grep 'iconId: "aws"' component-entries.ts` returns nothing).
  It is reachable only through the frozen legacy subtype path (`registry.ts:27-36`) or an
  explicit `.thf` `element.icon`.

The registry query API (`registry.ts:46-56`) exposes `getIcon`, `resolveElementIcon`,
`listComponents`, `searchComponents`, `listCategories`, `listProviders` — **no credits or
provenance accessor**. This issue adds one derivation function; it does not extend `Registry`.

### `icon-source-validation.ts` does not validate URLs

The issue brief suggested reusing it. It cannot be reused: its module header (`:1-14`) and its
exports (`parseIconSvg`, `isAllowedPathData`, `MAX_PATH_D_LENGTH`, `:203-207`) are entirely
about reducing an SVG document to constrained **path data**. It contains no URL handling, and
`no-runtime-svg-parser.test.ts` exists specifically to keep it out of the runtime bundle.

The only https enforcement in the repository is inside the audit test:
`new URL(p.sourceUrl).protocol` at `provenance-audit.test.ts:55` and
`new URL(entry.trademark.policyUrl).protocol` at `:105`. There is **no shared URL-safety helper**
(`grep 'protocol !== "https' src/` and `grep 'startsWith("https' src/` both return nothing
outside tests). Step 1 therefore adds one small predicate rather than pretending to reuse
something that does not exist.

### Both CSPs already forbid remote content, and nothing here needs relaxing

- Desktop: `tauri.conf.json` `app.security.csp` — `default-src 'self'`, `connect-src 'self'
  https://api.anthropic.com https://api.openai.com ipc: http://ipc.localhost`.
- Web: `public/_headers` — `default-src 'self'; script-src 'self'; …; connect-src 'self'
  https://api.anthropic.com https://api.openai.com`.

The credits surface performs no `fetch`, loads no image, and embeds no iframe. Registry data
and `NOTICE?raw` are compiled into the bundle at build time. External links are user-initiated
navigations handed to `openExternalUrl`, which neither CSP constrains. **No CSP change is
required, and proposing one would contradict `AGENTS.md:286`.**
`docs/knowledge/component-registry.md:84` already records the CSP as "unchanged and needs no
relaxation" for the registry work.

### Accessibility bar this project actually holds

### Scope gap found while reading: the GitHub mark ships outside the registry

`src/components/icons/github-icon.tsx:18-31` inlines the GitHub Invertocat as a hard-coded
`<path>`, used by the Settings Support section (`settings-dialog.tsx:18,355`). Its header
(`:10-13`) records the source (`https://github.com/logos`) and the brand-guideline constraints,
but it has **no registry entry, no `IconProvenance`, and no `NOTICE` row**, so no audit covers
it and this surface will not list it.

That is a real, honest limit on "every shipped third-party trademark owner". Two consequences,
both required:

1. The panel's copy must be literally true and scope itself to **component library** icons. It
   must not claim to cover every mark in the application.
2. A separate issue should decide whether the Invertocat needs an attribution/trademark record.
   It is proposed at the end of this plan and is **not** a sub-issue of #208, because deciding
   it requires a legal-posture judgement that #208's registry-derived scope does not contain.

## Decisions

### D1 — The UI reads the registry; `NOTICE` parity is asserted against the rendered output

**Decision.** A pure derivation over `ICON_ENTRIES` is the single source for the UI. No
generated artifact is introduced.

**Why.** The generated-artifact option was evaluated and rejected on evidence, not taste:

| Option | Verdict |
|--------|---------|
| UI reads `ICON_ENTRIES` through a pure projection | **Chosen.** `NOTICE` is already proved set-equal to `ICON_ENTRIES` in both directions (`provenance-audit.test.ts:131,137`). Add a second equality — projection ↔ `NOTICE` — and UI/`NOTICE` divergence becomes impossible by transitivity *and* is directly asserted. No new build step, no new file to go stale. |
| Generate a JSON artifact from the registry at build time | Rejected. It adds a generator, a committed generated file, and a *new* drift surface between "generated" and "committed" — the exact failure mode the issue is trying to prevent. It buys nothing: `icon-entries.ts` is already in the app bundle (`registry.ts:11` → the palette), so there is no bundle-size argument for it either. |
| UI parses `NOTICE?raw` into rows | Rejected for the structured lists. Turning prose back into records means a runtime parser over a Markdown-ish file whose format is enforced only by comment markers; a `NOTICE` edit that breaks the markers would degrade the shipped UI instead of failing CI. It *is* the right mechanism for the verbatim license text (D3). |
| Copy credits into JSX | Already rejected by the issue, and correctly. |

**What makes drift a build failure.** Three assertions, all inside `npx vitest --run`, which
`ci-local.sh:89` runs:

1. `buildIconCredits(ICON_ENTRIES).attributions` keyed as
   `` `${project} — ${license} — ${sourceUrl}` `` equals `parseNoticeBlock(noticeRaw,
   "icon-attribution")` as a `Set`, both directions.
2. The same for trademarks against `icon-trademarks`, keyed
   `` `${label} — ${owner} — ${policyUrl}` ``.
3. The **rendered DOM** of the credits section contains exactly those rows — asserted against
   the `NOTICE` blocks, not against the projection — so a component that quietly filters or
   truncates a row fails too. This is the assertion that closes the gap between "the data is
   right" and "the user sees it".

The marker parser is extracted from `provenance-audit.test.ts:34-46` into
`src/lib/registry/notice-blocks.ts` as a pure `parseNoticeBlock(noticeText, marker)` and imported
by both test files, so the two audits cannot disagree about how `NOTICE` is read. It takes the
text as a parameter and does **not** import `NOTICE?raw`, so it carries no bundle implication.

### D2 — Placement: a sixth Settings section, `licenses`

**Decision.** Add `licenses` to `SettingsTab` and one entry to `SECTIONS`, rendering a new
`<IconCreditsSection />`. Nothing existing moves.

**Why this survives #58, and why #58 is not a blocker.** The claim that #58 owns this surface
comes from `docs/plans/59-component-icon-registry.md:42-43` ("`#58` owns the settings/about
surfaces") and was repeated in a board-refresh comment on #208. **#58's own contract does not
support it.** `gh issue view 58` lists six acceptance criteria, all about the palette,
inspector, panel presets, and canvas — none mentions Settings or About. Its 1036-line committed
plan mentions `settings-dialog.tsx` exactly twice, both times to *reject* using it:
`docs/plans/58-panel-information-architecture.md:303` rejects `UserSettings` as a favorites
store, and `:1004` notes that `Reset to defaults` will not clear favorites. There is no
Settings/About restructuring anywhere in it.

This is deliberately conservative placement, and here is precisely what a future About issue
would move: one union member in `settings-store.ts:6`, one element of the `SECTIONS` array
(`settings-dialog.tsx:27-53`), and one self-contained component file. The section is a leaf with
no shared state, so relocating it is a re-import, not a rewrite.

**Rejected alternatives.**

- A new top-level dialog beside `KeyboardShortcutsDialog`. It needs its own store slice, its own
  menu-bar trigger, and its own focus handling — all IA decisions a future About issue may well
  reverse — to display content the issue explicitly asks to place "in the existing About/Settings
  information architecture".
- Adding it to the existing `Support` section. That section is a list of five outbound links
  (`settings-dialog.tsx:352-392`); appending ~15 rows of license data to it makes both jobs
  worse, and the deep link `openSettingsDialogAtTab("support")` (used by
  `status-bar.tsx:190` for `"ai"`) would land somewhere unpredictable.
- Relying on `/terms`. It exists (`terms-page.tsx:41-52`) and is exactly what the issue rejects:
  a marketing route the desktop app never navigates to.

**Label.** `Licenses`, with the lucide `Scale` glyph. "Credits" describes the intent; "Licenses"
is the word a redistributor scans a settings sidebar for. Owner validates — see *Owner
validation*.

### D3 — Ship the verbatim `NOTICE` text in the panel too

**Decision.** Below the derived lists, a collapsed `<details>` renders `noticeRaw` verbatim in a
focusable, scrollable region, mirroring `terms-page.tsx:41-52`.

**Why.** #208's problem statement names "redistributors" and "the nominative-use/withdrawal
policy" — neither is a set of rows. The MIT and ISC grants (`NOTICE:30-69`) and the trademark
prose (`NOTICE:74-81`) are text, and the only way to show text without drift is to show the
same bytes. `?raw` is already used identically at `terms-page.tsx:3` and builds today.

**Cost, stated rather than hidden.** `NOTICE` is 4,726 bytes. It is added to the chunk that
already contains `SettingsDialog`, which is statically imported by `app-layout.tsx:27` and so is
not lazily split. The section is therefore deliberately **not** lazy-loaded — a lazy chunk would
be unfetchable in exactly the offline scenario Step 4 tests. `LICENSE` (11,358 bytes) is **not**
embedded: it is Threat Forge's own Apache-2.0 text, already the desktop
`bundle.licenseFile` and already on `/terms`, and #208 is about icon credits.

### D4 — Link safety: one predicate, two live cases, no dead branch

External URLs are rendered as `<a href={url} target="_blank" rel="noopener noreferrer">` with an
`onClick` that calls `preventDefault()` and delegates to `openExternalUrl(url)`. That gives the
correct `link` role and a copyable address in both platforms while keeping the single code path
the repo already uses (`platform.ts:19-26` branches on `isTauri()` internally, so the component
needs no platform conditional).

`buildIconCredits` classifies each URL with an `isSafeHttpsUrl` predicate (`new URL(...)` in a
`try`, `protocol === "https:"`) and emits either a link target or a plain-text fallback. The
honest counter-argument is that `provenance-audit.test.ts:55,105` already fails CI on a non-https
URL, so the fallback is unreachable in any shipped build. It is kept anyway, for two reasons that
are checkable rather than rhetorical: this is the only surface that turns registry strings into
navigable targets, and the branch is **directly covered** by passing a synthetic entry list to
`buildIconCredits` — the same injected-data pattern `createRegistry` already uses and justifies
at `registry.ts:73-77`. It is a tested branch, not a defensive one.

`provenance-audit.test.ts` is **not** rewired to use the predicate. Leaving its inline
`new URL(...).protocol` checks alone keeps two independent derivations of the same rule and
avoids churning a delivered audit.

### D5 — Empty and error states, honestly

There is no error state, and this plan does not invent one. The panel reads a compiled-in
constant array; there is no fetch, no async, no I/O, and therefore no failure mode. A `try/catch`
or an error banner here would be fake completeness under `docs/quality/agentic-slop.md`.

Empty states that are real:

- Each of the three sections renders **only when its list is non-empty**. The withdrawn list
  genuinely can become empty (restoring the `amazonwebservices` mark would empty it), so this is
  a live case, covered by `buildIconCredits([])` and by a synthetic all-shipped list.
- If all three were empty the panel still renders its intro copy and the verbatim `NOTICE`
  disclosure, which is coherent. No "no credits found" message is added — the registry shipping
  zero icons is not a state this application can reach, and a message for it would be dead copy.

## Implementation steps

Each step is independently executable and `Low` on its own. Steps 1–4 map one-to-one onto the
sub-issues proposed at the end (Step 1 → 208a, Steps 2+3 → 208b, Step 4 → 208c).

### 1. Derive credits from the registry and prove the projection equals `NOTICE`

- **Behavior:** a pure function turns `readonly IconEntry[]` into three ordered, deduplicated
  lists, and a test fails the build if those lists stop matching the `NOTICE` blocks.
- **Files:**
  - new `src/lib/registry/credits.ts`
  - new `src/lib/registry/notice-blocks.ts`
  - new `src/lib/registry/credits.test.ts`
  - edit `src/lib/registry/provenance-audit.test.ts` (import extraction only)
- **Implementation:**
  1. `notice-blocks.ts`: move the body of `parseNoticeBlock`
     (`provenance-audit.test.ts:34-46`) into `export function parseNoticeBlock(noticeText:
     string, marker: string): string[]`. Behaviour identical, including the `throw` on a
     missing marker. It must not import `NOTICE?raw`.
  2. Update `provenance-audit.test.ts` to import it and delete the local copy. Do not touch any
     assertion in that file.
  3. `credits.ts`: define the result types and `buildIconCredits(entries: readonly IconEntry[])`.
     - `attributions`: for each entry with `artwork.kind !== "withdrawn"`, form the key
       `` `${provenance.project} — ${provenance.license} — ${provenance.sourceUrl}` ``; keep the
       first occurrence of each key in `entries` order. Each row carries `project`, `license`,
       `sourceRef`, `copyright` (may be `""`), and the source URL classified by
       `isSafeHttpsUrl`.
     - `trademarks`: for each shipping entry with `trademark.kind === "third-party"`, a row of
       `label`, `owner`, and the policy URL classified by `isSafeHttpsUrl`, in `entries` order.
     - `withdrawn`: for each entry with `artwork.kind === "withdrawn"`, a row of `id`, `label`,
       and `artwork.reason`.
     - `isSafeHttpsUrl(url: string): boolean` — `new URL(url)` inside `try`, `protocol ===
       "https:"`. Export it so the unit test can table-test it directly.
     - Narrow through the `ShippedIconEntry`/`WithdrawnIconEntry` discriminants
       (`types.ts:160-173`). No `as`, no non-null assertion — `AGENTS.md:270`.
  4. `credits.test.ts`: import `ICON_ENTRIES`, `noticeRaw` from `../../../NOTICE?raw`, and
     `parseNoticeBlock`. Assert:
     - `new Set(attributionKeys)` equals `new Set(parseNoticeBlock(noticeRaw,
       "icon-attribution"))`, and symmetrically for `icon-trademarks`. Both directions, as
       `provenance-audit.test.ts:131-149` does.
     - Order is `ICON_ENTRIES` first-appearance order (assert the four project/license pairs
       and the seven mark labels as arrays, not sets).
     - `withdrawn` is disjoint from `attributions` and `trademarks` — no withdrawn entry
       contributes attribution or trademark data.
     - `withdrawn` is non-empty for the shipped registry, with a failure message naming `aws` and
       telling a future contributor that emptying it means the live coverage in Step 2 is gone.
     - Synthetic-entry cases, built as literal `IconEntry[]` and passed to `buildIconCredits`:
       empty input yields three empty lists; a shipped-only list yields an empty `withdrawn`; an
       entry whose `sourceUrl` is `http://…` yields an unsafe-classified row; the same for
       `javascript:` and a malformed string.
     - `isSafeHttpsUrl` table: `https://x.test` true; `http://x.test`, `javascript:alert(1)`,
       `data:text/html,x`, `//x.test`, `""`, `"not a url"` all false.
- **Targeted verification:**
  `npx vitest --run src/lib/registry/credits.test.ts src/lib/registry/provenance-audit.test.ts`
  Discriminating check: temporarily delete one line from the `icon-attribution` block in
  `NOTICE` and confirm `credits.test.ts` fails naming the missing row, then restore it. A test
  that passes with `NOTICE` mutated is not testing anything.
- **Intent validation:** none for the owner at this step — it ships no user-visible behaviour.

## Cross-cutting requirements

- **Security and privacy:** no new trust boundary. All data is compiled in at build time; no
  input is parsed at runtime and no user or document data reaches this surface. Both CSPs
  (`tauri.conf.json` `app.security.csp`, `public/_headers`) are unchanged, as `AGENTS.md:286`
  requires. No new Tauri capability: `opener:default` is already granted
  (`capabilities/default.json:11`) and `openExternalUrl` is the existing adapter. Links carry
  `rel="noopener noreferrer"`. Registry URLs are constrained to `https:` by
  `provenance-audit.test.ts:55,105` and classified again by `isSafeHttpsUrl` at render (D4). No
  `dangerouslySetInnerHTML` — `NOTICE` is rendered as a text child of `<pre>`.
- **`.thf` compatibility:** none. No schema field, no version bump, no migration, no round-trip
  surface. `docs/knowledge/component-registry.md:1-5` records that the registry adds no document
  field, and this issue only reads it.
- **Browser and desktop:** one code path. `openExternalUrl` (`platform.ts:19-26`) is the only
  platform branch and it already exists. `?raw` embedding means both platforms read identical
  bytes; the desktop bundle additionally keeps `NOTICE` as a file resource
  (`tauri.conf.json` `bundle.resources`), which this change neither uses nor disturbs.
- **AI safety:** not applicable. No AI surface is touched, and the catalog read tool already
  excludes provenance and license fields by construction
  (`docs/knowledge/component-registry.md:143-147`).
- **Accessibility and UX:** semantic `section`/`h3`/`ul`/`li`/`a`; real anchors rather than
  buttons so the role and the address survive; the raw-text region is `tabIndex={0}` with an
  `aria-label` because `<pre>` is `generic` and takes no accessible name
  (`terms-page.tsx:34-45`); theme tokens only, gated by a scoped axe contrast scan in light and
  dark; `break-words` and a 900×700 overflow assertion. Empty and error states are handled per
  D5 — sections omit themselves when empty, and no error state is invented. The dialog's
  existing `Escape` handling and lack of a focus trap are unchanged and out of scope.
- **Observability and evidence:** the plan's evidence is the tests. Vitest carries the
  `NOTICE` parity and rendered-set assertions; Playwright carries the offline, keyboard, narrow
  window, and contrast evidence, with traces/screenshots retained on failure
  (`playwright.config.ts:24-26`).

## Risks and unverified claims

- **Unverified: Tauri `opener:default` scope.** `capabilities/default.json:11` grants
  `opener:default`, and `settings-dialog.tsx:358-390` already passes literal https URLs through
  `openExternalUrl`. Whether that default permission admits arbitrary https URLs at runtime, or
  requires a declared scope, was **not** confirmed — no desktop build was run and there is no
  test in this repository covering it. If it turns out a scope is needed, that is a
  least-privilege decision (`AGENTS.md:286`) and should be raised rather than widened silently.
- **Unverified: bundle-size delta.** `NOTICE` is 4,726 bytes on disk; the actual gzipped delta
  to the `app-layout` chunk was not measured, because no build was run during planning.
- **Risk: pre-existing Settings-dialog accessibility findings.** The tier-2 gate has never
  scanned the page with the dialog open — `accessibility-audit.spec.ts` opens it only inside
  `setReduceMotion` (`:14-23`) and the theme loop (`:70-80`), closing it before every scan. The
  dialog has no `role="dialog"`, no `aria-modal`, and no focus trap
  (`settings-dialog.tsx:74-78`). Step 4 therefore scopes its scan with `include` to
  `[data-testid="icon-credits"]`. If the implementer observes dialog-level findings while doing
  that work, they belong in a new issue, not in #208's diff.
- **Risk: `withdrawn` coverage is one entry deep.** If `aws` is ever restored, the live
  component-level coverage of that branch disappears silently. Mitigated by the synthetic-entry
  unit tests in Step 1, which do not depend on shipped data, and by the deliberate non-empty
  assertion with an explanatory failure message.
- **Risk: `NOTICE` marker fragility.** Both audits depend on the four HTML comment markers at
  `NOTICE:23,28,83,91`. `parseNoticeBlock` throws when one is missing
  (`provenance-audit.test.ts:37-39`), so deletion fails loudly; a marker *renamed* in both
  `NOTICE` and the parser would not. That is unchanged by this issue and is not made worse.
- **Not verified by reading: whether any icon-set upstream requires per-icon attribution.** The
  license allow-list (`types.ts:104-120`, `docs/knowledge/component-registry.md:86-98`) was
  chosen precisely so a single static notice discharges every one, and `CC-BY-*` is excluded.
  This plan relies on that prior decision rather than re-deriving it.
